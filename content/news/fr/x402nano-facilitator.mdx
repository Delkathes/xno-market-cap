## Ce qu'est x402

Le statut HTTP 402 Payment Required existe vraiment, défini dans la spécification mais presque jamais utilisé. x402 lui donne un rôle. Un point de terminaison protégé répond à une requête non payée par un 402 accompagné d'un en-tête `PAYMENT-REQUIRED` encodé en Base64 qui énonce les conditions : schéma accepté, réseau, prix, adresse du destinataire. Le client signe un paiement et réessaie avec un en-tête `PAYMENT-SIGNATURE` ; le serveur vérifie, règle, puis sert le contenu.

Le protocole est agnostique à la chaîne, et désormais géré par la x402 Foundation, dont la Linux Foundation a annoncé le lancement opérationnel. Ce facilitateur implémente le versant Nano.

## Pourquoi ça colle

x402 vise les micro-paiements machine à machine : un agent IA qui paie par appel d'API, par inférence. Ces montants sont minuscules, et c'est là que les frais font le plus mal. Sur des rails payants, un paiement d'une fraction de centime est dévoré avant même d'arriver. Sur Nano, il se règle en moins d'une seconde, sans frais.

## Comment un paiement circule

La documentation décrit le flux en cinq étapes :

1. Un client demande une ressource protégée.
2. Le serveur répond 402, avec `PAYMENT-REQUIRED` qui transporte les schémas acceptés, le prix, le réseau et l'adresse Nano du destinataire.
3. Le client construit un bloc d'envoi Nano, le signe et génère la preuve de travail.
4. Le client réessaie avec les données de paiement encodées en Base64 dans `PAYMENT-SIGNATURE`.
5. Votre serveur transmet les données au facilitateur, qui valide la signature du bloc et le diffuse sur le réseau Nano. Le résultat revient dans `PAYMENT-RESPONSE` ; une fois confirmé, le serveur sert le contenu.

## Pas de compte, pas de clé API

Sans permission : c'est le mot juste. Pas d'inscription, pas de clé, pas de tableau de bord : pointez votre serveur vers l'URL et c'est parti. Un en-tête `x-api-key` ou Bearer optionnel ne sert qu'à activer les statistiques d'usage dans un tableau de bord. Les erreurs reviennent dans un format JSON cohérent (400 corps invalide, 401 clé invalide, 429 limite de débit, 500 erreur serveur), et les limites sont de 200 requêtes par minute et par IP pour `/facilitator/verify` et `/facilitator/settle`.

## Le point de vue développeur

Deux SDK couvrent l'intégration. `@x402/next` donne aux développeurs Next.js `paymentProxy` (intergiciel qui protège les routes de pages) et `withX402` (enveloppe les gestionnaires de routes API). `@x402/core` expose `HTTPFacilitatorClient` avec vérification et règlement manuels pour Express, Hono ou n'importe quelle infrastructure. Les deux pointent vers la même URL :

## Débuts timides, lecture honnête

La section agents IA de la documentation est ce qui rend le projet intéressant. Un agent peut découvrir de façon autonome un point de terminaison protégé, lire les conditions de paiement, signer un bloc Nano, calculer la preuve de travail et réessayer : pas d'humain, pas de compte, pas de carte. C'est exactement le flux pour lequel Nano a été conçu.
